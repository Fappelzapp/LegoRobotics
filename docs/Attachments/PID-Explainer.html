How your PID code works

Your robot drives forward but wants to point at a certain angle. A gyro measures the angle. A short piece of maths decides how hard to steer. That is the whole idea — and this page lets you play with it until it stops being magic.

The one idea

You already know how a PID works

You have used one this morning. In the shower.

🥿 The shower

You want 38 °C. You feel the water. It is 34 °. You have an error of 4 °. So you turn the hot tap a little. You feel again. 36 °. Smaller error, smaller turn. 37.5 °. Almost nothing.

The bigger the error, the bigger the push. That single sentence is 80 % of a PID.

🤖 The robot

You want heading 0 °. The gyro says 12 °. The error is 12 °. So you steer a little. The gyro says 6 °. Smaller error, smaller steer. 1 °. Almost nothing.

Same loop, different sensor. Your code does exactly this, 20–50 times per second.

The three letters

Each letter is a different way of reacting to the error. Your code uses two of the three. The third is switched off.

P

Proportional

“How wrong am I right now?” Push in proportion to the error. A big error gets a big push. This alone gets you most of the way there.

your code: kp = 4
I

Integral

“How long have I been wrong?” Adds up the error over time. Fixes a stubborn offset (a robot that always stops 3 ° short).

your code: ki = 0  — off
D

Derivative

“How fast is the error shrinking?” If you are closing in quickly, ease off early. This is the brake that stops you overshooting.

your code: kd = 1
steering = 4 × error + 0 × (sum of errors) + 1 × (change in error)

Read that as: steering = Kp × P + Ki × I + Kd × D. The three K numbers are the “gains”. Tuning a robot means choosing them.

The loop, as a picture

i

One rule decides everything. The loop is only stable if a positive steering value pushes the robot in the direction that makes the error smaller. If it pushes the wrong way, the error grows, so the push grows, and the robot spins away. That is called positive feedback, and it is the failure you will see most often in this file.

1
Three inputs, one output-free function

stp = setpoint, the heading to hold. speed = how fast to drive. amount = how far, in the code's own distance units. It drives, then returns.

2
Sign flip #1

Whatever speed you passed in, the function works with the opposite sign from here on. Every later speed in this function is the flipped one. This is one of three sign operations that must agree; see Check these.

3
The whole tuning, in three lines

Kp 4 — four units of steering for every degree of error. Ki 0 — integral off. Kd 1 — a small brake. Changing robot behaviour means changing these three numbers, and nothing else in the function.

4
Zero the odometer

The wheel counters start at 0, so strecke measures this move only. Note it is links.angle() — motor degrees. If there were a gear between motor and wheel, this number would be wrong.

5
The stop condition

Keep looping until the counted distance reaches amount. The or kurvejanein == 2 part is a leftover switch that is never turned on anywhere in the file, so ignore it — it is dead code.

6
A print in every single pass

Printing is slow, and it makes each pass take a different amount of time. Slow, uneven passes are exactly what makes the Kd term unpredictable, because Kd reacts to “change since last pass”, not “change per second”.

7
The speed ramp

Three cases: arriving (slow down proportionally to what is left), setting off (add 5 per pass through anfahren instead of jumping straight to full speed), and cruising (just use speed). This is a simple, hand-made acceleration curve — not part of the PID.

8
Why the robot still rolls at the end

The braking formula bottoms out at roughly half of speed, never at zero. So when the loop exits, the robot is still moving — which is why nearly every call in the program is followed by motors.stop().

9
The measurement

g = Gierwinkel = the gyro's heading in degrees. This is the “where am I?” half of the loop. It is read fresh on every pass, which is good.

10
The error, and its sign

Forward motion uses g − stp; reverse uses ≤stp − g. The two branches exist so that driving backwards still corrects in the right direction. If one branch is written the other way round, the robot steers away from the target and the error grows without limit.

11
The derivative — no time in it

derr is “error now minus error last pass”. There is no division by elapsed time, so at a 30 Hz loop the same Kd is three times stronger than at 10 Hz. Change the loop rate and your tuning changes too.

12
The integral — accumulating forever

Every pass adds the error to a running total. It is never limited and never reset. Harmless today because Ki = 0 multiplies it by zero — but the day someone sets Ki to 0.1, this number will have been growing for the whole move, and the robot will lurch when it is finally used.

13
The one line that matters

ric = Kp·err + Ki·errsum + Kd·derr. Everything else in this function is either measuring, smoothing the start, or counting distance. int() throws away the fraction — Python's int() truncates towards zero, it does not round.

14
Sign flip #2

Multiply the steering by the direction of travel again. Combined with flip #1 this is what makes the same code work forwards and backwards. It also means two flips cancel — so it is worth testing on the floor which way the robot actually goes.

15
The push

motors.drive(ric, speed_local) — the PID result first, the speed second. Check this one against your PyBricks version: the published signature is drive(speed, turn_rate), speed first. See Check #1 for a 30-second test you can do with the robot on blocks.

16
Counting the distance

The two wheels turn in opposite directions as numbers (because the motors are mounted mirror-image), so subtracting them adds up instead of cancelling. Divide by two, convert degrees to turns, multiply by the wheel circumference. Full explanation in Distance.

1
Same idea, much simpler

ausrichten means “to align”. This one turns the robot in place until it points at stp. It uses only P — no I, no D — plus a constant 30.

2
The risky stop condition

while g != stp means “until exactly equal”. If the heading lands on 34 when you asked for 35, and the push is not enough to move it, this loop can spin forever. A tolerance (abs(g-stp) < 2) would be safer. In practice the constant 30 usually rescues it.

3
1800, not 180

This branch is supposed to handle the “go the short way round” case for angles over 180 °, but it checks 1800 °. The gyro would need to be five full turns away before it triggers, so in practice this branch never runs. Almost certainly a typo.

4
P, with a kick

(stp − g) × (−5) is proportional control with gain 5. The ±30 is a constant nudge added in the same direction — the minimum effort that actually makes the motors move against friction. Without it the robot would creep to a stop a few degrees short.

5
Both wheels, same speed

Running both drive motors at the same speed makes the robot pivot on the spot. Note it uses the raw motors, not motors.drive() — you can do that because motors.stop() was called and the drive base is not driving.

 1def motors_kurve1(target_angle, speed, steering): 21    MIN_SPEED = 50 3 4    while True: 5        current_angle = hub.imu.heading() 6        remaining = target_angle - current_angle 72        if abs(remaining) <= 3: 8            break 93        if abs(remaining) < 10:10            drive_speed = max(MIN_SPEED, abs(remaining) / 10 * abs(speed))11        else:12            drive_speed = abs(speed)13        drive_speed *= 1 if speed > 0 else -1144        motors.drive(-steering, -drive_speed)15        wait(20)165    motors.stop()
1
Never stop before arriving

MIN_SPEED = 50 is a floor: even at the very end the robot keeps creeping. That avoids the “stuck two degrees short forever” problem at the cost of a little overshoot.

2
A proper tolerance

abs(remaining) <= 3 — this is the safe way to stop. Compare with ausrichten, which waits for exact equality. This function is the better pattern.

3
Gentle finish

In the last 10 ° the drive speed is scaled by how much is left, so the robot eases in instead of slamming to a stop. Note this only slows the forward speed, not the steering.

4
Two minus signs

drive(-steering, -drive_speed). Whether these two minus signs are needed depends on the same sign convention as Check #2. With an odd number of sign errors the robot turns the opposite way to what you asked.

5
This loop does wait

wait(20) gives a steady 50 loops per second — better than motors_pid, which has no wait at all. A steady loop is what makes a PID repeatable.

Telling the hub which way is up

top_side and front_side describe how the hub is mounted. They decide what “heading 0” means. Get them wrong and every angle in the program is shifted.

2

The Bluetooth button becomes stop. Good habit at a competition — you do not want to chase a robot across the table to switch it off.

3
Drive motors

rechts = right on port A, links = left on port E. No direction override is given, so both count clockwise as positive — that is why the two angle() readings have opposite signs when driving straight.

4
The attachment motors

modull/modulr are the left and right arms. profile=None turns off the smooth acceleration ramp, so run_angle jumps to speed immediately. For competition arms that is usually what you want: fast and predictable.

Why the two wheel counters are subtracted

The two drive motors are mounted as mirror images, so when the robot goes straight forward one counter climbs and the other falls:

degLinks = +1000 # climbs degRechts = −1000 # falls degMittel = (1000 − (−1000)) / 2 = 1000

Subtracting therefore adds them. If you added instead, you would get zero and the robot would think it had not moved.

The rest is just one wheel's turn count turned into a distance:

strecke = (degMittel / 360) × 5.56 × π # turns # diameter # = turns × circumference (cm) 1 turn → 5.56 × 3.1416 = 17.47

Note abs() before the division: the counter works for reverse too, but always adds to strecke.

The big picture

What the program actually runs

Seven routes, one after the other. Each one waits for the same two-button handshake before it starts, so you choose when the robot begins each leg.

→

The ritual: press RIGHT, then press LEFT. The robot beeps, resets the gyro to 0 °, and starts that route. It is not a menu — every route runs in order.

—

Two parts of the file are switched off

There are two blocks of ''' in the source. In Python, three quotes start a text string — so everything between them is not code. That is how the four module-helper functions and the #test block at the very bottom end up doing nothing at all.

The “menu” only picks a variant

ausgewaehlter_weg looks like a menu with a break, but it only chooses between two versions of one route. Routes 4–7 come after it and still run. Read the file top to bottom, not as a menu.

Honest review

Ten things worth checking on the robot

These are questions, not verdicts. Your robot has been driving, which means most of this already works somehow. Each item comes with a test short enough to actually do.

!

Nothing in this section was tested on a hub. It comes from reading the code and from the published PyBricks documentation. The tests are what turn a guess into a fact.

1

Is motors.drive() getting its arguments in the order you think?

PyBricks documents the signature as drive(speed, turn_rate) — speed first in mm/s, turn rate second in deg/s. Your code calls motors.drive(ric, speed_local), which puts the PID output first.

30-second test: with the robot on blocks (wheels off the floor), run motors.drive(200, 0) for a second. If the wheels roll forward, speed really is the first argument. Then run motors.drive(0, 90) and see whether it spins.
datasheet not tested on your hub docs.pybricks.com, v2.0 / v3.5 / v3.6 / stable
2

Which way does a positive steering value turn the robot?

The loop is only stable if a positive ric pushes the error towards zero. Your error is computed as roughly g − stp, so a positive error means “pointing too far clockwise”. Positive steering must therefore turn anticlockwise. If it turns clockwise, the loop is positive feedback and the robot spirals away.

Test: put the robot on the floor, aim it roughly forward, and run motors_pid(0, 400, 10). Watch the first second. Does it curve back to 0° (good) or further away (sign inverted)?
inference not tested
3

abs(g - stp) > 1800 looks like it means 180

In all three ausrichten functions the “take the short way round” branch triggers above 1800° — five full turns — instead of 180°. So it never fires, and the robot always turns the long way. Harmless for small angles, visible after a big turn like ausrichten2(-150) following a heading of +100.

Test: change 1800 to 180 in one copy and see whether the -150° turn after Weg 4 gets quicker and less wobbly.
inference
4

while g != stp can loop forever

That is an exact-equality test on a rounded float. If the heading settles on 34 while you asked for 35, and the ±30 kick is not enough to move it, the loop never ends. Everything else in the file uses inequalities; this is the odd one out.

Test: replace with while abs(g - stp) > 2: and compare how the turns feel. Add a loop counter if you want a hard safety stop.
inference
5

Heading is never wrapped to ±180°

hub.imu.heading() keeps counting past 180 and past 360; it does not wrap. So a robot at heading 210 asked to hold −150 has an “error” of 360° and will spin all the way round. Only motors_curve_gyro uses abs() to dodge this.

Test: in a copy, print the heading after a long sequence. If you ever see a number outside −180…360, this is already affecting your route.
datasheet
6

The two wheel sizes disagree by 12 %

DriveBase(wheel_diameter=62.4) versus 5.56 × π in the distance formula. One of them is a calibration, the other is the truth. See Distance for the arithmetic.

Test: tape-measure a motors_pid(0, 300, 30). 30 cm means 5.56 is right; about 33.7 cm means the formula under-counts.
inferencenot measured
7

The loop has no wait() and prints every pass

Two consequences: the loop rate is whatever Python manages that moment, and Kd depends on that rate because derr has no time in it. A loop that runs at 50 Hz on the bench and 20 Hz while printing over Bluetooth is tuning a moving target.

Test: remove the print(), add wait(10), and see whether the straight lines get straighter. If they do, the print was costing you accuracy.
inference
8

errsum is never limited and never reset

Harmless while Ki = 0. The day someone sets Ki to 0.1, the sum will already be huge from the first few seconds of the move, and the robot will lurch. If you ever enable I, clamp the sum and reset it at the start of every move.

Test: set Ki = 0.05 and watch the first straight. If it swerves hard at the start, that is the accumulated sum arriving all at once.
inference
9

Every move is followed by motors.stop() for a reason

The braking formula bottoms out around half of speed, so the loop ends with the robot still rolling. The stop() calls are not decoration — they are part of the move. If one is ever missing, that leg will overshoot.

Test: count the motors_pid(...) calls and the motors.stop() calls. Find the one pair that does not match.
inference
10

Three functions and one switch do nothing

ausrichten3, motors_kurve and motors_curve_gyro are never called. kurvejanein is never set to 2, so its branches never run. None of this is a bug — it is just 90 lines you can stop reading.

Test: nothing to test. This is a licence to ignore them.

If you have never written Python — the eight things this file uses
  • Variable — a named box. kp = 4 puts 4 in a box called kp.
  • Function — a named recipe. def motors_pid(...) defines one; motors_pid(0, 500, 21) runs it with those three ingredients.
  • Argument — an ingredient. The three numbers in the brackets.
  • if / elif / else — choose a path. Only one branch runs.
  • while — repeat until the condition stops being true. This is what makes it a loop.
  • Indentation — the spaces at the start of a line are the structure. Four more spaces means “inside the block above”.
  • int(...) — throw away the decimal part. int(4.9) is 4, and int(-4.9) is −4 (it truncates towards zero; it does not round).
  • # — a comment. Python ignores the rest of the line. So does your robot.

A unit like motors.run(200) means “run the motor at 200 degrees per second”. Motor speed is in deg/s; motor position is in degrees. Neither is a distance in centimetres until you multiply by the wheel.
