# 2026-10-28 PID Explainer

## Observations

Read-only findings from the pasted source, all **inference** unless labelled otherwise:

- `motors_pid()` calls `motors.drive(ric, speed_local)` — PID output first. The published PyBricks
  signature is `drive(speed, turn_rate)`, speed first (**datasheet**: docs.pybricks.com v2.0, v3.5,
  v3.6 and stable). Recorded as a question with a 30-second test, not as a verdict — the robot has
  been running, so the installed behaviour is the open question.
- The distance formula uses `5.56 × π` while `DriveBase` is built with `wheel_diameter=62.4`. That
  is a factor 1.122. Arithmetic: `amount = 21` → 23.6 cm, `amount = 30` → 33.7 cm. Whether 5.56 is
  a deliberate calibration or a stale constant needs a tape measure.
- `abs(g - stp) > 1800` in all three `ausrichten` functions. The comment says 180°. The branch
  therefore never runs. Looks like a typo but was **not** changed.
- `while g != stp` is an exact-equality stop condition on a rounded float.
- `errsum` is never clamped and never reset; harmless only while `ki = 0`.
- `ausrichten3`, `motors_kurve` and `motors_curve_gyro` are never called. `kurvejanein` is never
  set to 2. Two `'''` blocks disable the module helpers and the `#test` block.
- `motors_curve_gyro` uses `axle_track = 120` internally while `DriveBase` was built with 106.

## Changes and decisions

- Created `docs/Attachments/PID-Explainer.html` — one self-contained page, no external assets, no
  CDN, works offline in a browser and from Obsidian.
- Structure: a plain-language introduction and a "Start here — 6 clicks" walkthrough; an
  interactive heading-PID simulator with live `err / derr / errsum / ric / strecke` readouts; the
  four key functions annotated line by line; a distance-calculation explorer; cards for the unused
  blocks; the eight-route program flow with per-call translations; ten review questions each with
  a short robot test; a German-to-English glossary.
- The **simulator is illustrative, not a model of this robot.** It reproduces the code's control
  law and discrete loop, with a first-order turn lag so that high `Kp` visibly oscillates. Its
  steering scale and inertia are chosen for readability and labelled as such on the page.
- Deliberately did **not** "fix" any of the findings above in the source, because there is no
  source file in the vault and no hub test was possible.

## Validation and limits

- **Hub: not run — no hub connected.** Nothing on the page has been confirmed against the real
  robot.
- Offline checks performed on `docs/Attachments/PID-Explainer.html`:
  - HTML parsed with `html.parser`: no unclosed or stray tags after fixing three malformed
    `<span>`s.
  - JavaScript extracted and bracket-balanced with string/comment stripping; all 54 `getElementById`
    references resolve to existing elements.
  - Loaded in headless Chrome (`--headless=new`): no console errors; all 8 mission rows and 20 step
    rows generated by script; canvases painted.
  - Simulator driven through the "Step once" control for 80 passes and compared with a Python
    re-implementation of the same equations. Default gains: `strecke = 45.4`, verdict *clean,
    settled 0.43 s, 1 overshoot*. `Kp 12 / Kd 0.5`: verdict *nervous, 4 crossings*. Flipped steering
    sign: runaway, as intended.
  - Light and dark themes both rendered and screenshotted. Temporary screenshots were deleted.
- **Not tested:** touch interaction on a tablet, Firefox/Safari rendering, and whether Obsidian
  opens the attachment in the system browser rather than inline.
